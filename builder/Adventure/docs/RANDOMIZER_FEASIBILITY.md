# Randomizer feature and in-game menu feasibility

This is a planning record for the development randomizer, not a claim of Ship of Harkinian compatibility. The comparison is with [Ship of Harkinian's randomizer](https://www.shipofharkinian.com/randomizer); its settings are a reference for player-facing behavior, not code to copy. Cosmetics are outside this comparison.

## Access gate investigation

The following are leads from the local v2.3.2 game resources, not verified implementations. The Door of Time, Jabu-Jabu and trial controls enable experimental live flag probes on a development build; they do not yet establish that the gates open. Zora Fountain remains disabled. Test the transitions and save behavior in game, including an existing save and a fresh save.

For the forest gates, [OOTRR's open-world plan](https://github.com/ootrando/ootrr/blob/0fa64f4/randomizer/core/src/slice/support.rs) clears both `KokiriForest_Npc_Kokiri_Mido_Child_Blocker` and `KokiriForest_Npc_Kokiri_007_Child_Blocker_00` at new-game initialization. Its [opening edit](https://github.com/ootrando/ootrr/blob/0fa64f4/randomizer/core/src/start_defaults/opening.rs) also advances the authored `Meet_DekuTree` opening request to `Step03`. Its [starting-reward stage](https://github.com/ootrando/ootrr/blob/0fa64f4/randomizer/core/src/start_reward.rs) inserts the flag writes into `Sequence/SetPouchAndStatusForGameStart.module.ainb`; changing a new-save default alone is not evidence that later initialization will preserve it. Its open-forest setting covers both gates, so a separate open-Deku-only mode still needs its own story and gameplay verification here. OOTRR is GPL-3.0-or-later; retain its attribution and license notices if porting code or data.

The local supported game has one opening `Meet_DekuTree` request (event 11), and both blocker flags are persistent Bools defaulting to true. `HAL_OpenForestOpening.PatchQuestStep` rewrites that request's `StepName` from `Step01` to `Step03` with the relocation-safe string writer. An authored fixture and a local offline probe pass, including after the opening camera skip. The experimental overlays set the appropriate new-save defaults rather than inserting OOTRR's initialization actions; whether later story events overwrite them remains unverified. Existing saves retain their stored flags.

In an isolated fresh-save run with both settings enabled, the two blocker flags were false after the opening, remained false while walking in Kokiri Forest, and were still false after reloading its autosave. Neither physical gate crossing, the later Deku quest, nor either setting on its own was verified; see the local tested-configuration rows for the hardware and build.

- **Door of Time:** `DoorOfTime` sets `Market_Child_TimeTempleDoor_Opened`, a persisted Bool with a false default. The same flow also advances the Door of Time challenge and handles age transition events. Determine which door and sword interactions consume the flag, and preserve the authored age-change sequence; setting the flag alone does not establish that the whole route works.
- **Zora Fountain:** King Zora's child actor is present in the Domain map without a simple placement condition; its conversation is associated with `Get_StoneOfWater`. Trace the letter, movement, collision and quest branches before bypassing him, while keeping the letter quest usable.
- **Jabu-Jabu:** the child Fountain map conditions the mouth airwall on the inverse of the persisted `JabJabOpenedMouth` Bool. The eating event is part of `Get_StoneOfWater`, and the actor and dungeon entry have separate behavior. Verify the mouth animation, collision, entry and subsequent quest before treating that Bool as sufficient.
- **Skip trials:** the castle map references six separate `HavePlayedEvent.InsideGanonCastle_Dungeon_BarrierRemove_*` states and also contains a tower barrier actor with no direct placement condition. Trace the barrier logic and completion events; marking trial cinematics played is not evidence that the central barrier is removed or that the final route is safe.

These are launch-time gameplay options, not part of the seed's immutable access model. The probes repeatedly set live flags while enabled; the game may save resulting story state, so use a backup. Current placement safeguards do not account for any of these access options.

## Menu boundary

The C# migration includes seed generation and validation, runtime overlay composition, BYML and event-flow edits, resource-size tables, managed Zstandard/dictionary decoding, seed identity checks, cosmetics and icon preparation. A synthetic end-to-end seed matches the Python content hash, and authored resource fixtures cover the migrated edits. Broader comparisons on local resources and in-game verification are still needed. The shared Hookshot game build pipeline remains Python.

`HAL_RandomizerSeedService.GetCapabilities()` is a read-only launcher-core query for the four current seed inputs. It is not callable by the native game. Seed generation and validation run in C# before launch; the launcher passes the validated overlay and starting state through the process environment. Existing profiles bind their seed and resource hashes. The overlay and startup state must not be changed under a running save.

A future in-game interface needs a native, versioned bridge, with explicit ownership and lifetime rules. Candidate operations, **not yet implemented**, are:

1. `get_capabilities()` returns supported options, allowed values, scope restrictions, and whether each takes effect only on a new seed or at a safe live point.
2. `get_active_seed_summary()` returns a validated, non-spoiler summary of the current profile's immutable seed and settings. A tracker would require separate observed-check state and must avoid exposing placements by default.
3. `validate_draft(settings)` reports unsupported combinations and logic limitations without changing a save or overlay.
4. `request_seed_generation(profile, seed, settings)` hands a request to a trusted launcher/service outside the running game. Progress, cancellation, errors and atomic publication need a defined protocol; generation must never replace the active profile's seed or overlay.
5. `get_runtime_options()` and `set_runtime_option(id, value)` could handle independently reviewed live-safe enhancements only. Each needs a documented thread boundary, persistence policy and rules for when the change takes effect. Seed settings remain immutable for an existing profile.

The present launcher C# method is useful for exploring presentation but is not that bridge. A native bridge must establish where profile identity comes from, authenticate and validate requests, prevent concurrent writers, and preserve the existing marker and resource-hash checks. It also needs cross-platform packaging of the generator and its dependencies; the current helper requires a source checkout. The renderer API is versioned: changing `MkwVkHost` or `MkwVkRenderer` requires an API version bump. No renderer API change or menu is proposed until the boundary and game-state hooks are demonstrated.

## Suggested sequence

First establish a reviewed location/collection and access model beyond the opening, with tests for unreachable and duplicate rewards. Then implement one currently disabled reward family end to end, including persistence and a local playthrough, before broadening its checkbox. In parallel, prototype the bridge as a read-only seed summary and capability query; only then consider draft validation and generation for a new profile. Live changes and trackers need their own verified state hooks. This order keeps an attractive menu from implying that unsupported settings or seeds are safe.
